# P11.1 — Legacy shift pointer deprecation, slice review

2026-11-10. First proposed implementation slice for P11. Reviewed by the Orchestrator with the Security reviewer; every line reference was checked against the working tree. No code was written, no schema or migration was touched, and the shared Git index was not modified.

## Why this slice comes first

The pointer `users.shift_id` is a legacy compatibility field, not an authoritative schedule. It is currently writable through three paths, and only one of them is legitimate. Closing the other two is a small, self-contained change that removes a scheduling write that bypasses effective dating and audit, and it removes the last obstacle to the assignment path being the single writer.

The slice does not remove the column. The owner approved beginning the deprecation now and keeping the column, so the database is untouched and the change is reversible by reverting the code.

## Exact code scope

**Backend, validators** — `backend/validators/index.ts`: the `shiftId` field stays declared in `createUserSchema.body` (`:83`) and in `updateUserSchema.body` (`:99`), but as `z.never(...).optional()`. A request without the field is valid, and a request that carries it is refused with a clear message naming the field, rather than having it stripped in silence. The message tells the caller that a shift is set through an assignment. The `shiftId` fields in the policy, registration and export schemas are different fields and stay.

**Backend, controller** — `backend/controllers/userController.ts`:

- `:15` — remove `shiftId: true` from `PUBLIC_USER`, so the field leaves every user projection.
- `:84-88` — delete the `validShift` helper. Its only callers are `:154` and `:177`, so it becomes dead code.
- `:154` — delete the `validShift` call in the create path.
- `:177` — delete the `validShift` call in the update path.
- `:159-162` and `:176-185` — the writes spread the parsed object, never the raw body. The schema refuses the field, so the parsed object cannot carry it, and the controller parses the body itself, so the protection does not depend on the middleware.
- A small helper reports the reason for a rejected field: the legacy pointer has its own wording, and every other field keeps the original generic wording. A request that carries the pointer is refused before any write, so the audit never claims a field that was not written.

**Backend, the remaining writer** — `backend/controllers/assignmentController.ts:91-94`: keep the pointer write, which becomes the only writer, and add `businessId` to its `where` clause. The clause currently carries only the id, which is a tenant-safety gap on the one write this slice keeps.

**Backend, API documentation** — `backend/docs/swagger.ts`: remove `shiftId` from the user schema (`:104`), the create request (`:120`) and the update request (`:133`).

**Frontend** — no change. `src/types/index.ts` carries no `shiftId` on the user type, and no screen reads the field off a user object. The `shiftId` references in `src/pages/HrReports.tsx`, `src/pages/Policies.tsx` and `src/pages/Scheduling.tsx` are shift, policy and assignment payloads, and the ones in `src/test/msw-handlers.ts` are attendance fixtures.

**Database** — no change. The column, its foreign key and its index stay.

## API compatibility effects

| Surface | Effect | Severity |
|---|---|---|
| `POST /api/users`, `PUT /api/users/:id`, `PATCH /api/hr/employees/:id` | A `shiftId` in the body is refused with a 400 and a field error naming `shiftId` | Deliberate. A caller that used to set the pointer is told plainly that it cannot, and that a shift is set through an assignment |
| `POST /api/hr/employees/:id` | Same | Same |
| `GET /api/users`, `GET /api/users/:id`, `GET /api/hr/employees` | The `shiftId` key disappears from every user response | Breaking for any client that reads it. No client in this repository does |
| `GET /api/audit` | Unchanged | None |
| Assignment routes | Unchanged, and the pointer they write is unchanged | None |

The breaking surface is the response key. It is a field no screen in the repository reads, and the field's purpose is deprecated, so removing it is the point of the slice rather than a side effect. A client that still reads it will see `undefined` and fall back to the assignment list, which is the intended path.

## Security tests

1. HR cannot move the pointer through `PATCH /api/hr/employees/:id`. The response is 400 with a field error naming `shiftId`, and the stored `users.shift_id` equals its value before the request.
2. A `shiftId` sent on `POST /api/users` is refused. The response is 400 with a field error naming `shiftId`, and no account is created.
3. The user projection no longer exposes the pointer. The response keys of `GET /api/users/:id` do not contain `shiftId`.
4. The assignment path remains the only writer. After a successful assignment create, `users.shift_id` equals the assigned shift.
5. The pointer write is tenant-scoped. The assignment update carries `businessId` in its `where` clause.
6. The audit reason does not name a field that was not written. A refused request writes no audit row at all, and a request without the pointer never names it.
7. No route accepts the pointer. Both account schemas refuse it, and the field is absent from every user response.

## Acceptance criteria

- The create and update schemas refuse the field with a clear message, and the public projection omits it.
- No frontend or backend consumer reads the field from a user object.
- The assignment path is the only writer, and its write is tenant-scoped.
- The audit trail never names the field as changed.
- The column, its foreign key and its index are unchanged in the database.
- The backend unit and contract suites pass, the typechecks pass, and the security scan is clean.
- The staged diff contains no migration, no schema and no RLS change.

## Related work in the same phase

**Durable assignment audit.** The assignment path writes its audit to stdout only (`backend/controllers/assignmentController.ts:99,214` call `auditLog.assignmentCreated` and `auditLog.assignmentDeactivated`), while the contract row for the create route promises an audit. The schedule path will write durable rows through the transaction client, so the two paths would behave differently. The pattern to copy is `persistAudit` in `backend/controllers/userController.ts:89-94`, which calls `tx.auditLog.create` directly and therefore commits or rolls back with the write it describes. The shared `writeAudit` helper accepts a transaction client but swallows insert failures (`backend/utils/auditWriter.ts:100-111`), so it is not sufficient as the only guarantee. This belongs to phase P11.2 and is recorded there.

**History preservation.** Nothing in this slice deletes or rewrites history. The pointer column stays, the assignment rows are untouched, and no realized period is edited. The deprecation stops at this stage; the later stages, and the removal of the column, need their own owner approval and, for the column, an owner-approved destructive migration that exports the evidence first.

## Open items carried into this slice

- The deprecation stages beyond this one are unapproved. The pointer becomes a cache, then stops being written, and the column is dropped, and each stage needs its own approval.
- The retirement signal window is a proposal, not an approved value.
